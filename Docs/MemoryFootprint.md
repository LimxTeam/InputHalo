## 已确认的额外分配与改动

1. **字体整文件拷贝**：原来用 vector 完整读取 Segoe UI（0.92 MiB）、微软雅黑 TTC（18.79 MiB）、
   宋体 TTC（17.47 MiB）和 Arial（1.00 MiB），约 38.2 MiB 私有堆。
   现由 HarfBuzz 的 Windows 文件映射读取，FreeType 与 HarfBuzz 共用同一只读映射，
   字体对象销毁时释放。保留原字体回退覆盖范围；映射页仍可能计入共享/总工作集，并非零成本。
2. **字形图集过大**：初始 2048² R8 单页 4 MiB，CPU 快照、每帧 GPU 图集、上传缓冲存在多个副本。
   改为 1024² 单页 1 MiB，按需增长，最多 8 页。没有通过降低文字分辨率减少占用。
3. **上传缓冲长期保留**：GPU 已完成字体上传后仍保留暂存缓冲。
   现在在同一帧资源下次安全复用时回收，保留同步和字体快照寿命约束。
4. **隐藏设置仍保留绘图资源**：收起或最小化设置后，释放其交换链、帧资源和绘图缓存；
   重新打开或拖动窗口前重建，不影响独立的桌面叠加层资源。
5. **调试版本口径**：此前日常启动的是 Debug，加载 Vulkan 验证层和调试运行库。
   现在提供本地 Release 可执行程序供手动使用，保留 Debug 构建配置用于开发。

没有调用 EmptyWorkingSet、强制分页或定时清空工作集来制造低读数。

## 为什么不能直接承诺 2–3 MiB

当前是 C++ / Vulkan / D3D11 / DirectComposition 的硬件合成架构，包含中英文字体、
按显示器分配的共享纹理、交换链以及图形驱动。一个 4K RGBA8 图像的逻辑像素就有 31.64 MiB；
这是图形资源尺寸，**不能直接等同于进程物理内存或与工作集相加**。共享导入的 Vulkan/D3D 纹理也不能重复计算。
系统、驱动、分辨率、DPI、窗口状态和已打开页面都会影响数值。

本轮已移除可确认的浪费，但没有达到 2–3 MiB。若这个数字是硬性产品约束，
需要另立轻量渲染架构验证（例如小面积 GDI/系统绘图叠加窗口），并重新权衡文字、透明合成和动画效果；
不能仅通过几个配置开关保证现有架构满足。

后续可研究只为实际可见内容分配小区域叠加窗口、共享每设备的字体纹理以及按需创建次屏资源；
这些涉及多屏绘制、同步和跨屏轨迹，需要独立迭代，不应未经验证直接替换现有合成路径。
